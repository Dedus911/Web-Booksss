# КнигоМнение

Курсовой проект: сайт, где люди пишут рецензии на книги, читают ленту, ставят лайки и дизлайки и ведут профиль.

Сделано на **Python + Django**, база — **SQLite**, страницы — обычные HTML-шаблоны и один файл CSS. Сторонних библиотек нет: в `requirements.txt` одна строка. Код намеренно простой: все вьюхи — обычные функции, без классов, без REST API и без JavaScript. Так его легче читать и объяснять.

## Что умеет сайт

| Что | Где |
| --- | --- |
| Регистрация (логин, пароль, подтверждение пароля), сразу после неё — вход; почту не спрашиваем | `/signup/`, `views.signup` |
| Вход / выход — готовые вьюхи Django, мы только дали шаблон | `/accounts/login/`, `/accounts/logout/` |
| Лента рецензий: поиск по книге/автору/заголовку, фильтр по жанру, сортировка, по 5 на страницу | `/`, `views.feed` |
| 16 стартовых жанров создаются сами: классика, ужасы, фэнтези, триллер и другие | `reviews/migrations/0002_start_genres.py`, `0003_more_genres.py` |
| Написать рецензию: книга, заголовок, текст, оценка 1–5 | `/review/new/` |
| Просмотр рецензии, редактирование и удаление только своим автором | `/review/<номер>/`, `.../edit/`, `.../delete/` |
| Лайки и дизлайки: один человек = одна реакция, повторное нажатие снимает оценку, лайк можно поменять на дизлайк | `views.react`, кнопки в `_reactions.html` |
| Добавить книгу, если её нет в списке; после добавления сразу открывается форма рецензии с выбранной книгой | `/book/new/` |
| Страница книги со всеми рецензиями о ней | `/book/<номер>/` |
| Профиль: «о себе», любимый жанр, число рецензий, полученных лайков и дизлайков | `/user/<логин>/`, `/profile/edit/` |
| Админка для жанров, книг и рецензий | `/admin/` |

## Как запустить у себя

Команды выполняются в папке проекта (там, где лежит `manage.py`).

```bash
python -m venv .venv
source .venv/bin/activate          # на Windows: .venv\Scripts\activate
pip install -r requirements.txt
python manage.py migrate           # таблицы и стартовые жанры
python manage.py createsuperuser   # логин и пароль для /admin/
python manage.py runserver
```

Открой `http://127.0.0.1:8000/`.

Жанры добавлять руками не надо: миграции `0002_start_genres` и `0003_more_genres` сами кладут в базу 16 жанров — от классики и фантастики до ужасов, фэнтези и триллера. При желании список можно дополнить в `/admin/`.

В базе уже есть демонстрационные пользователи, книги и рецензии, поэтому можно сразу нажать «Войти»:

| Логин для входа | Пароль | Как подписан на сайте |
| --- | --- | --- |
| `anna` | `Kursovaya2026!` | Анна |
| `mark` | `Kursovaya2026!` | Марк |
| `lena` | `Kursovaya2026!` | Лена |

В ленте и в профилях авторы подписаны по-русски; логин нужен только для входа.

Дальше порядок такой:

1. Войди демо-логином или зарегистрируйся (кнопка «Регистрация»).
2. «Добавить книгу» → заполнить поля → сразу откроется форма рецензии.
3. Опубликуй рецензию, зайди в ленту, поставь лайк.

Проверить всё автоматически:

```bash
python manage.py test
```

Должно выполниться 8 тестов: открытие ленты, стартовые жанры, регистрация без почты, отсутствие поля почты на входе и регистрации, запрет писать рецензию гостю, создание профиля, работа лайка, запрет править чужую рецензию.

## Данные на другом компьютере

Файл `db.sqlite3` лежит прямо в репозитории, поэтому логины, хеши паролей, книги и рецензии переезжают на другой ПК вместе с кодом. После клонирования не нужно ничего заполнять заново: `pip install -r requirements.txt` → `python manage.py runserver` → «Войти» под `anna`.

Пароли хранятся не текстом, а хешами Django, поэтому переносятся безопасно; в открытом виде их нигде нет.

Если ты завёл **свой** аккаунт или написал новую рецензию и хочешь увидеть их на другом компьютере, надо закоммитить изменившуюся базу:

```bash
git add db.sqlite3
git commit -m "Добавил свои рецензии"
git push
```

Два важных замечания:

- если на другом ПК уже есть старый `db.sqlite3` (созданный раньше командой `migrate`), перед `git pull` удали его или переименуй — иначе git не сможет заменить файл;
- не удаляй `db.sqlite3` просто так: вместе с ним исчезнут все логины и рецензии. При работе сайта файл немного меняется (сессии, время последнего входа) — это нормально.

## Как это устроено

### Модели (`reviews/models.py`) — это таблицы в базе

| Модель | Что хранит |
| --- | --- |
| `Genre` | жанр, просто название |
| `Book` | название, автор, год, жанр, описание, кто добавил |
| `Review` | книга, автор рецензии, заголовок, текст, оценка 1–5, дата |
| `Reaction` | пара «пользователь + рецензия» и число: `1` — лайк, `-1` — дизлайк |
| `Profile` | ссылка на пользователя, «о себе», любимый жанр |

Связи: у книги много рецензий, у пользователя много рецензий, у рецензии много реакций. `related_name` позволяет писать по-человечески: `review.reactions.all()`, `user.reviews.all()`.

В `Reaction` стоит `unique_together = (("review", "user"),)` — база сама не даст одному человеку оставить две реакции на одну рецензию. Поэтому не нужна отдельная проверка «а вдруг он уже лайкал».

У `Review` есть три маленьких метода: `likes_count()`, `dislikes_count()` и `stars()` (превращает оценку 1–5 в «★★★☆☆»). Django умеет вызывать такие методы прямо из шаблона, без аргументов.

Профиль не создаётся при регистрации. Есть простая функция `get_profile(user)`: она делает `get_or_create`, то есть отдаёт профиль, а если его нет — создаёт. Благодаря этому не пришлось разбираться с сигналами Django.

Жанры на новой базе появляются из двух миграций: `0002_start_genres.py` (первые 6) и `0003_more_genres.py` (ещё 10, включая ужасы и фэнтези). Это обычные миграции, но вместо создания таблиц они вызывают функции, где по списку имён выполняется `Genre.objects.get_or_create(name=...)`. Миграции выполняет команда `migrate`, поэтому все 16 жанров готовы сразу и на любом компьютере. `get_or_create` нужен, чтобы при повторном запуске не появились копии.

### Вьюхи (`reviews/views.py`) — функции «запрос → база → страница»

| Функция | Что делает |
| --- | --- |
| `feed` | собирает рецензии, применяет поиск `Q(...)`, фильтр по жанру, сортировку, `Paginator` на 5 штук |
| `signup` | проверяет `SignUpForm`, создаёт пользователя и сразу логинит его |
| `review_add`, `review_edit`, `review_delete` | формы рецензии; чужие рецензии недоступны через `get_object_or_404(..., author=request.user)` |
| `review_detail`, `book_detail`, `profile` | страницы одной рецензии, книги и пользователя |
| `react` | лайк/дизлайк по нажатию кнопки |
| `book_add`, `profile_edit` | формы книги и профиля |
| `mark_my_reactions` | помощник: заранее помечает, какую кнопку подсветить у текущего пользователя |

`@login_required` — декоратор: если человек не вошёл, Django отправит его на `/accounts/login/?next=...` и после входа вернёт обратно.

### Как работает лайк, по шагам

1. В шаблоне под каждой рецензией две маленькие формы с `method="post"` и `{% csrf_token %}`. Скрытое поле `next` запоминает, с какой страницы нажали.
2. `POST` идёт на `/review/5/react/like/`. Вьюха `react` пускает только вошедших пользователей и только `POST` (случайно зайдя по ссылке через GET ничего не изменится).
3. `get_or_create` ищет реакцию этого пользователя на эту рецензию. Нет — создаёт. Есть и та же самая — удаляет (снял лайк). Есть другая — меняет число на противоположное.
4. `redirect(next)` возвращает человека на ту же страницу, лента обновляется уже с новыми счётчиками.

Счётчики считаются методами `likes_count()` / `dislikes_count()`, то есть всегда берутся из базы, а не хранятся отдельным числом, которое может «разъехаться».

### Шаблоны

`base.html` — общая шапка, навигация и сообщения. `_review_card.html` — карточка рецензии (её переиспользуют лента, страница книги и профиль), `_reactions.html` — кнопки лайка, `_form.html` — вывод полей любой формы. Если надо поправить вид сразу всех форм, правится один файл.

Стили в `static/css/style.css` написаны руками, без Bootstrap: не надо тянуть CDN, всё работает офлайн. Аватарки сделаны просто первой буквой логина — так не пришлось настраивать загрузку картинок.

## Шпаргалка для защиты

**Короткий рассказ на 2 минуты:**

> Тема — платформа для обмена рецензиями на книги. Я сделал веб-приложение на Django: одно приложение `reviews`, пять моделей в базе, страницы на HTML-шаблонах. Регистрацию и вход я взял из стандартного `django.contrib.auth`: готовые формы плюс свои шаблоны, почту не запрашиваю — только логин, пароль и его подтверждение. Главная страница — лента: она достаёт рецензии из базы, умеет искать по книге и автору, фильтровать по жанру и разбивать выдачу по страницам. Рецензию может написать только вошедший пользователь, а править и удалять — только её автор. Лайки и дизлайки лежат в отдельной таблице `Reaction`, где уникальная пара «пользователь + рецензия» не даёт накручивать оценки; повторное нажатие снимает реакцию. Профиль показывает данные человека и статистику по его рецензиям. Жанры и демо-данные попадают на новый компьютер сами: жанры — миграциями с данными, пользователи и рецензии — готовым файлом `db.sqlite3` в репозитории. Всё проверил восемью автотестами.

**Вопросы, которые могут задать, и честные ответы:**

| Вопрос | Что ответить |
| --- | --- |
| Почему Django, а не чистый Python? | У Django уже есть пользователи, сессии, формы, защита от CSRF, админка и ORM. Я не изобретаю авторизацию заново, а пишу логику сайта. |
| Почему вьюхи-функции, а не классы? | Для такого небольшого проекта функции нагляднее: видно, где запрос, где проверка, где сохранение. Ничего не спрятано в родительском классе. |
| Где хранятся пароли? | В таблице `auth_user`, которую создаёт Django. Пароль хранится в виде хеша, в открытом виде нигде; сравнивает их Django сам. |
| Как защищены формы? | `{% csrf_token %}` в каждой форме плюс `CsrfViewMiddleware` в настройках. Без токена `POST` не пройдёт. |
| Как сделана регистрация? | `UserCreationForm` от Django: логин, пароль, подтверждение пароля. Почту не спрашиваем, поэтому в форме нет ни одного лишнего поля. После сохранения сразу логиню пользователя функцией `login()`. |
| Откуда берутся жанры на новом компьютере? | Их добавляют две миграции с данными, `0002_start_genres` и `0003_more_genres`: внутри обычный Python-код с `get_or_create`. Всего 16 жанров. Миграции выполняет `migrate`, значит список появляется сам. |
| Как логины и рецензии попадают на другой ПК? | Вместе с файлом `db.sqlite3`, который лежит в репозитории. Пароли хранятся хешами, поэтому переносятся безопасно. |
| Почему нельзя лайкать дважды? | `unique_together` в модели `Reaction`: база не даст создать вторую строку с той же парой. Плюс кнопки видны только вошедшим. |
| Почему лайк хранится числом 1 / -1? | Одна таблица вместо двух, удобно считать суммы и легко поменять лайк на дизлайк: просто обновляем поле. |
| Чем `select_related` помог? | Лента тянет рецензии вместе с книгами и авторами одним запросом, а не делает отдельный запрос на каждую карточку. |
| Почему SQLite? | Для курсовой не нужен отдельный сервер БД: база — один файл, который можно положить в репозиторий и перевезти на другой компьютер. На реальном сайте заменил бы на PostgreSQL, поменяв блок `DATABASES`. |
| Что бы добавил дальше? | Комментарии, загрузку обложек, подписки на авторов и AJAX, чтобы лайк ставился без перезагрузки страницы. Сейчас специально оставил обычные формы — так логику проще показать. |

**Что намеренно упрощено** (это не ошибки, так задумано для учебного проекта):

- нет загрузки картинок: аватар — первая буква логина, обложек нет;
- лайк работает через обычный `POST` с перезагрузкой страницы, без JS и AJAX;
- почта при регистрации не запрашивается: для курсовой хватает логина и пароля, поэтому нет и восстановления пароля по почте;
- нет комментариев и подписок;
- база `db.sqlite3` лежит прямо в репозитории: для курсовой это удобно, данные переезжают на другой ПК, но в настоящем проекте базу в git не держат;
- счётчики лайков считаются отдельными запросами — при десятках рецензий это незаметно, а код понятнее;
- `DEBUG = True`, `SECRET_KEY` лежит в `settings.py`, `ALLOWED_HOSTS = ["*"]` — это удобно на защите, но для боевого сайта так делать нельзя;
- в `settings.py` есть `CSRF_TRUSTED_ORIGINS` с адресом демонстрационной ссылки, чтобы формы работали, когда сайт открыт не с localhost. При обычном запуске дома эта строка ни на что не влияет.

## Если что-то не завелось

| Проблема | Решение |
| --- | --- |
| `ModuleNotFoundError: No module named 'django'` | активируй виртуальное окружение и выполни `pip install -r requirements.txt` |
| `no such table: reviews_review` | выполни `python manage.py migrate` |
| Порт занят | `python manage.py runserver 8001` |
| `403 CSRF verification failed` | обнови страницу и войди заново; токен привязан к сессии |
| Не подходит демо-пароль | `python manage.py changepassword anna` задаст новый |
| Лента пустая | значит, удалили `db.sqlite3`: верни файл из репозитория (`git checkout -- db.sqlite3`) или скачай архив заново |
| `git pull` ругается на `db.sqlite3` | удали или переименуй локальный файл базы, потом повтори `git pull` |
| Забыл пароль админки | `python manage.py changepassword <логин>` |
